# Web loading phrases: mobile parity and skeleton replacement

Status: implemented 2026-09-17.

## Outcome

Replace web skeletons with the mobile app’s vertically cycling loading phrases. Preserve the exact mobile copy and each feature’s phrase selection. Keep the real navigation, headings, and available content visible while the affected content region loads.

Graphify queries were used for orientation; the web graph had no matching loader nodes. Findings below were verified against current source files, including existing uncommitted changes. This is a source audit; animation has not yet been checked in a running browser.

## What exists today

- Mobile `src/components/shared/LoadingCaption.tsx` shuffles once per mount and changes phrase every **1,800 ms**. Each keyed text enters with `SlideInDown.duration(450)` and exits with `SlideOutUp.duration(450)`. Its clipped wrapper is 34 px high; text is centered, 13 px, medium weight, secondary color.
- Mobile `src/components/shared/LoadingPhrase.tsx` cycles in supplied order, with the same **1,800 ms / 450 ms** timings. Its clipped wrapper is 22 px high, stretches to its parent width, and allows caller-controlled alignment/type styling.
- Web `src/components/LoadingCaption.tsx` already contains the complete general set, but swaps text every **1,400 ms** in one unkeyed span. `src/App.css` applies an opacity pulse; there is no outgoing/incoming vertical transition. It shuffles after mount to avoid SSR mismatch.
- Web investments contains 6 of mobile’s 14 phrases. Bill scan history contains 6 of mobile’s 10. Recurring, archive, scan processing, individual scan detail, and general copy already match.
- Web Money Brain uses general phrases while waiting for its first answer; mobile uses its dedicated six-phrase chat set.
- Active skeleton markup is in `ExpensePageSkeletons.tsx`, `TransactionsView.tsx`, and `InsightsPage.tsx`. `EnvelopesPage.tsx` uses a static loading block named `erd-skeleton-block`.
- Other gaps are text-only states, blank modal returns, export states, and subscriptions hidden behind the dashboard’s aggregate loading condition.

## Shared implementation

1. Add `src/lib/loadingPhrases.ts` with the exact inventory below and per-set ordering metadata. Use one typed feature key per set. General is the fallback for surfaces without a specialized mobile equivalent, including Insights; do not invent new phrases.
2. Upgrade the existing `LoadingCaption` rather than create another competing animation. Use keyed incoming/outgoing text layers, clipped by a stable wrapper: old text moves from center to above, new text moves from below to center, simultaneously over 450 ms, on a 1,800 ms cadence. The existing `motion` dependency can implement presence and transforms; no additional package is needed. Match easing visually against mobile during implementation rather than claim a browser curve is identical without checking.
3. Expose page, section, and inline placement plus alignment. Preserve `className`/`style` compatibility during migration. Page means the available content area, never an overlay that hides navigation. Inline supports left-aligned row copy; section centers within a panel body.
4. Retain SSR-safe deterministic initial output, then shuffle only the sets mobile shuffles. Ordered sets must preserve their supplied order. Stabilize phrase arrays; clean up intervals on unmount; reset safely on feature changes; support empty/single-item input without modulo-zero or needless timers.
5. Use secondary theme text, approximately mobile’s 13 px medium type. Reserve stable height for the longest phrase at each breakpoint, including wrapping at narrow widths and enlarged text. Do not blindly copy mobile’s 22 px box when a web phrase needs two lines. Avoid zero-width absolute-positioned text and clipping.
6. Under reduced motion, show a stable phrase without sliding. Mark the affected region busy. Provide one stable accessible loading status per region and hide the changing decorative phrase from repeated live announcements; do not announce new copy every 1.8 seconds.
7. Show loaders for initial unresolved data only. Preserve populated content during background refreshes. Stop loading immediately on success or failure; provide actual empty/error/retry states. Do not add artificial delay to let the animation finish. Keep short action labels such as Saving, Deleting, and Restoring on their buttons; long-running export generation gets its dedicated phrase nearby.

## Boundaries and secondary cases

- `app/account/page.tsx` currently shows a static mobile-download link for Wrapped, not a fetched availability card. Include **wrappedStatus** in the catalog for parity but do not animate this static link or introduce a status endpoint just to consume the set. If a live availability card is restored later, place the inline ordered loader in its blurb.
- `app/(auth)/code/page.tsx` has an empty auth-card Suspense fallback; `app/account/security/page.tsx` has a null Suspense fallback. These are not skeleton systems. If expanding the rollout to these visible route waits, use a stable neutral accessible “Loading…” label with the same loading wrapper; the mobile catalog has no authentication/security set, and playful budget copy is inappropriate for sign-in. No new phrase set is required for this migration.
- Mobile `app/loading.tsx` itself returns null. Do not mistake it for the animated loading implementation.
- Existing scan artwork, upload status, buttons’ mutation labels, image placeholders and content entrance animations are separate from skeleton replacement.
- No new route-level `loading.tsx` is required just for parity. If a route fallback is introduced later, reuse the same loader and avoid nesting simultaneous route/page loaders.

## Acceptance and verification

- Exact text parity for every imported set, including curly ellipses and contractions; full list lengths retained. Test actual ordered versus shuffled behavior, not just implementation details.
- Fake-timer component checks: 1,800 ms cadence, outgoing and incoming layers during 450 ms overlap, interval cleanup, feature changes, single/empty input and reduced-motion behavior. If addressing the existing animation mismatch as a bug, reproduce it with a failing test before changing the component, per project TDD instructions.
- Browser checks with deliberately delayed requests: desktop and narrow web layouts, light/dark themes, 200% text zoom, fast cache hits, slow initial loading, background refetch, errors and empty data. Confirm old phrase exits upward while the next enters from below; no clipping, horizontal jumping or residual shimmer.
- Verify dashboard loads independently of slow subscriptions, subscription errors do not stall the budget, chat loader stops on the first delta, export loader stops on failed/ready jobs, and dialog close controls remain functional while loading.
- Verify SSR hydration produces no mismatch and assistive technology receives one useful status instead of a repeated announcement loop.
- Run targeted component/integration tests, then web typecheck and production build. Run applicable lint checks and distinguish pre-existing issues in the dirty working tree. No tests/build were run for this documentation-only audit.
